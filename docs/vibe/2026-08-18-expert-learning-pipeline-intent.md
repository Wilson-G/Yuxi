# 专家学习流程改造：意图冻结与共识说明

日期：2026-08-18

状态：意图已冻结。本文已纳入 2026-08-18 评审意见，作为后续方案讨论、开发和验收的共同依据。

开发分支：`feat/expert-learning-pipeline`

## 这份文档解决什么问题

Yuxi 已经完成了专家 Skill 引擎的第一阶段：材料包可以上传、整理成 Skill、启用，并在对话中通过检索原文辅助回答。这条路线证明了产品入口、后台执行、Skill 安装和运行时消费可以成立。

接下来的改造不是继续增强“文件整理和索引”，而是让系统真正从材料中学习：理解老师如何判断，形成可复用的笔记和专题讲义，最后编成一个有方法、有导航、能实际回答问题的专家 Skill。

这次改造涉及流程、模型调用、后台任务、项目进度和用户确认，跨度较大。如果只按某个旧实现或某次口头讨论推进，很容易逐渐变成另一套东西。因此先冻结我们真正认可的产品意图，后续技术设计必须服务于这里的共识。

这是一份共识和讨论文档，不是数据库表、接口字段或代码模块的详细设计。没有在这里固定的技术细节，可以在实现阶段根据 Yuxi 的现有结构做最小、直接的选择；已经在这里固定的用户流程和职责边界，不应被实现方式悄悄改变。

## 中央 Prompt 设计规范

第 0 阶段的中央 Prompt 设计规范位于
`backend/package/yuxi/expert/prompt_designer/`。它是本流程的正式输入，不是实现内部的隐藏资产：

- `SKILL.md` 规定怎样从代表材料设计项目专属 Prompt，并明确讲义必须把判断手艺教材化；
- `templates/` 提供不同材料类型的调研起点；
- `examples/` 提供完整阶段 Prompt 的结构示例，只学习结构，不携带某领域的写作政策。

项目 Prompt 生成时必须读取这套规范。项目学习方案、编译底稿和阶段 Prompt 包由第 0 阶段依据它与实际样本生成，用户确认后才固定到项目中。用户同时选择人工模式或自动推进；中央规范修改只影响之后新建或重新定向的方法版本。

来源纪律用于防止把材料外内容混入方法，不能替代方法本身。讲义的主线必须是“什么局面 -> 先看什么 -> 怎样判断 -> 为什么 -> 什么条件会改变处理”；人名、案例范围、来源差异和材料缺口只在它们实质改变判断时说明。编译过程不生成泛化的医学、法律、金融或合规声明，运行时安全要求另行处理。

## 一句话目标

把一批已经能够可靠阅读的材料，经过“定学习方法、逐份学艺、组织专题、编成 Skill”的过程，变成一个真正可用的专家 Skill。

整个过程由 Yuxi 内部完成：复用当前项目已有的文档转正文、模型调用、后台任务、进度展示和 Skill 启用能力，不接入 Pi，也不把旧项目的复杂工厂系统搬进来。

## 对原迁移意图的正式修正

原迁移说明里提到 Pi，是因为旧项目用 Pi 批量派发模型任务。我们现在确认：要迁移的是它背后的任务方式，而不是 Pi 这个外部执行工具。

需要保留的方式是：

```text
当前任务需要的完整输入
+ 已确认的项目学习方案
+ 明确的任务要求和输出约定
-> 调用一次模型
-> 得到一个结果
-> 检查并保存
```

Yuxi 本身已经能够调用配置好的模型，也有后台任务和并发执行能力，因此这些工作应在当前系统内部完成。

这里的“完整输入”不表示把几十份材料一次交给一个模型。它表示每个任务需要什么，系统就把这些依赖完整、明确地组装好，不让模型自己进入工作区找文件，不让它猜测上下文，也不依赖之前的对话历史。

例如：

```text
一份完整口述稿 + 项目学习方案
-> 一份学艺笔记

原稿 + 当前笔记 + review 标准
-> 一次笔记复核

原稿 + 当前笔记 + 具体修改意见
-> 一次定点修订

某个主题需要的已通过笔记 + 主题方案
-> 一篇专题讲义
```

Pi 不再是前置条件，也不进入当前改造的运行依赖。

## 并行助手与总编

第 1 阶段和后续编辑阶段解决的是两类不同问题，不能使用同一种并发方式。

逐份阅读材料的目标是扩大覆盖面，适合由普通模型任务并发完成；主题取舍、讲义写作、冲突口径和最终 Skill 的回答方式需要统一作者性，由一个项目内串行执行的总编角色负责。

第一版先使用 Yuxi 已配置的模型调用完整跑通这条主链，不接入 Prime、不建设 Prime 工作台，也不做 Prime 高级问答。总编是业务职责，不是特定模型产品：第一版由当前模型承担项目学习方案、主题地图、讲义定稿和全书收口；未来接入 Prime 时，只替换总编执行者，不改变项目状态、产物、用户确认点、证据边界或发布流程。

双方分工如下：

| 工作 | 承担者 | 运行方式 |
| --- | --- | --- |
| 完整材料阅读、笔记、笔记 review | 普通模型任务 | 每份材料独立并发 |
| 候选主题、证据包、冲突和遗漏清单 | 普通模型任务或 Reviewer | 为总编并发准备输入 |
| 项目学习方案、主题地图和讲义小样 | 总编模型 | 串行决定项目方向 |
| 单篇讲义的证据核对和遗漏检查 | 普通模型任务或 Reviewer | 可并发检查 |
| 讲义正文、关键修订和编辑方案更新 | 总编模型 | 同一项目内串行定稿 |
| 全书一致性、导航和最终 `SKILL.md` | 总编模型 | 串行收口 |

普通助手提供研究结果，不能直接改变主题地图、统一口径或正式讲义。即使未来允许并发产生讲义研究稿，这些稿件也只是总编输入，不能经简单拼接后进入最终 Skill。第一版优先并发准备证据和执行 review，由总编模型逐篇形成或实质性定稿最终讲义。

总编不是流水线控制器。它不决定项目什么时候推进、不领取整个项目的全部后台任务，也不直接修改项目正式状态或启用 Skill。Yuxi 负责范围、调度、状态、门禁和发布；总编负责需要统一作者性的编辑判断。

### 编辑方案承载连续判断

“同一个总编”表示同一个项目只有一个最终编辑判断入口，不表示依赖一个永不结束的 ACP 会话。总编的连续性由项目中持续更新的“编辑方案”承载，而不是由模型会话记忆承载。

编辑方案只保留当前有效内容：

```text
项目学习方案
+ 主题地图和每个主题的笔记、证据范围
+ 已确定的术语、冲突处理和写作口径
+ 已完成讲义的状态与简要结论
+ 尚未解决的问题
```

它保存编辑决定和产物映射，不重复复制所有材料、笔记和讲义全文。执行当前总编任务时，Yuxi 根据映射提供当前编辑方案、当前主题所需的完整笔记与证据、当前稿件和 Reviewer 的具体意见。

编辑方案只有总编任务可以提出更新，最终仍由 Yuxi 校验并提交。普通并发助手只能提交候选主题、证据和问题，不能同时改写全局编辑决定。同一项目内，任何会改变编辑方案或正式稿件的总编任务都必须保持单一写入者；不同项目可以并行运行各自的总编任务。

## 我们所说的“学习”是什么

这套流程不是把文档切碎后做摘要，也不是单纯建立一个能搜到原文的索引。

我们希望最终 Skill 学到的是材料中的判断方式，包括：

- 老师关注什么信号；
- 如何从现象走到判断；
- 一个结论成立的条件和边界；
- 遇到例外或冲突时如何处理；
- 哪些内容可以形成稳定方法，哪些只适用于特定案例；
- 面对真实问题时，应该如何组织答案和给出行动建议。

材料可能来自同一位老师，也可能来自同一领域的多位老师。多位老师不自动意味着必须拆项目。相同观点可以并列汇合；有冲突的观点应保留来源、前提和适用条件，不能为了得到一个整齐结论而强行揉在一起。

一份材料如果没有值得迁移的判断，也允许被标记为“已阅读但不入选”。这是一种正常结果，不需要为了完成数量强行生成笔记。

## 材料进入学习前的边界

模型不直接承担 Word、PDF、PPT、Excel 等二进制文件的读取和解析。文件必须先通过 Yuxi 已有的文档处理能力转换成模型可以直接阅读的可靠正文，再进入专家学习流程。

整体边界是：

```text
原始文件
-> 转换为可读正文
-> 形成有意义的材料单元
-> 进入专家学习流程
```

这一层可以做必要的机械检查，例如：

- 是否成功得到正文；
- 正文是否为空或明显乱码；
- 文件是否有无法处理的错误；
- 单份材料是否超过当前模型一次能够完整阅读的范围。

这一层不负责判断材料内容好不好，也不在这里重新解释材料。

如果材料超过模型一次可读取的范围，不能静默截断，也不能让代码暗中抽取其中一部分。它必须在进入学习前被整理成有业务意义的自然单元，例如一篇文章、一节课、一份口述稿或一个完整主题。不能到了模型调用时再按字符数随意切成失去语义的片段。

代码只接收和传递已经明确形成的材料单元。如果一份材料无法完整放入所选模型的上下文，又无法形成有意义的自然单元，就进入“需要处理”，由用户缩小范围、重新整理或拆分项目，不能带着不完整正文继续学习。

## 完整流程

### 第 0 阶段：确定这个项目应该怎么学

系统从上述中央 Prompt 设计规范、材料类型模板和结构示例出发，先读取材料目录与基础信息，再完整阅读用户确认的代表材料：当前可用材料不足 4 份时全部选择，达到 4 份后选择 4～20 份并尽量覆盖不同方向。系统据此探测这批材料的领域、表达方式、说话人关系、案例结构和判断特点。第 0 阶段不提前逐份学习整个材料包；它的作用是决定这批材料后续应该怎样被学习和编写。

用于探测和小样的材料优先由用户指定。用户没有指定时，系统只能依据用户可见的材料信息，例如标题、来源、作者、类型和长度，按上述数量规则提出候选并说明选择理由，由用户确认后再完整读取。程序不能按文件位置、字符数或其他隐藏规则自行截取正文，也不能暗中决定哪一部分具有代表性。

探测先形成项目定向报告：当前领域和材料类型是什么、材料如何传授判断或经验、哪些来源关系与保真风险会影响学习、最终读者需要一位怎样的专家。它不是笔记，也不替后续阶段提炼每份材料的知识。

总编模型再依据中央方法、材料类型模板和项目定向报告，形成完整、自洽、只属于当前项目的编译底稿和阶段 Prompt 包。它们必须自然写成当前领域的语言，而不是“通用规则 + 一段项目补丁”。这套 Prompt 要让后续模型从一开始就知道这批材料应该怎样阅读、什么是好笔记、review 关注什么、讲义如何组织，以及最终专家应以怎样的身份、判断方法和边界面对读者。

第 0 阶段的可见产物包括：

- 人可以直接读懂的项目学习方案；
- 必要时可以展开查看的原始 Prompt；
- 可用材料不足 4 份时全部试跑；达到 4 份后，从确认样本中选择 4～5 份真实材料并发生成笔记小样；
- 小样对应的 review 结果。

系统在这里停下来，让用户确认一件事：

> 这样学习这批材料，对不对？

如果不对，调整项目学习方案、编译底稿和阶段 Prompt 包并重新生成小样；自动修订后仍存在会影响批量学习的具体问题时，当前方法不能继续，必须调整后重新试跑。通过 Review 后，用户确认的是当前“项目方法版本”：项目学习方案、编译底稿和完整阶段 Prompt 包一起固定在项目中。UI 默认展示人能读懂的学习方案和小样，Prompt 包只作为可展开查看内容。

这次确认同时提供“自动推进”开关。新页面默认开启，但只有确认请求提交的 `auto_advance` 才写入项目；数据库字段和旧 API 请求默认关闭，保证历史项目与旧调用方继续使用人工流程。自动推进开启后，这次确认是候选 Skill 成书前最后一次人工确认：系统可以在现有 Review 和总编边界内自动完成方法校准、逐份学习、主题组织、讲义编写与候选 Skill 组装，不再等待方法 V2 或组织方式确认。关闭时保留当前人工流程和两个确认点。

自动推进只授权生成候选成品，不授权发布。无论使用哪种模式，最终 Skill 都必须先供用户预览，再由用户手动启用。

后续由用户反馈或重新定向触发、会改变笔记、Review、主题或讲义语义的 Prompt 修改，都必须创建新的项目方法版本，并重新生成小样等待用户确认；不能在已确认项目中悄悄替换底层 Prompt。自动模式中，第一次确认明确授权的有限方法校准可以形成 V2 并复跑同一批小样，不再新增人工确认。

中央模板只用于创建新项目。模板以后修改，不得悄悄改变已经开始或已经确认的项目。

### 第 1 阶段：逐份学习材料

系统以自然材料单元为并发单位。每份材料独立完成：

```text
完整材料
-> 生成学艺笔记
-> review 笔记是否学对
-> 必要时带着具体意见最多修订两次并复核当前笔记
-> 得到通过的笔记、明确不入选，或进入需要处理
```

不同材料可以并发处理；同一份材料内部仍按“撰写、review、修订”的顺序执行。一份材料失败时，只处理这一份，不重新运行已经完成的材料。

review 只做四类明确判断：

- 通过，进入后续主题整理；
- 有明确问题，可以定点修订；
- 明确没有迁移价值，记为“不入选”；
- 无法自动解决，进入“需要处理”。

Reviewer 给出具体修订意见时，系统在同一材料任务内最多执行两次“修订 + 复核”。人工模式中，两次复核后仍要求修订，保留最后笔记和具体意见，材料进入“需要处理”，由用户重跑或明确排除。自动模式中，最后一次有限修订后由模型作出最终判断：采用当前笔记，或把材料记为 `no_value` 并保留原因；代码不能按修订次数或材料数量机械排除。作者认为当前材料不能形成可迁移判断且 Reviewer 认可时，两种模式都直接记为“不入选”。

第 1 阶段只有在每份材料都得到明确结果后才能交接：

- “已通过”的笔记进入主题规划；
- “明确判定不入选”的材料不进入主题规划，但保留在项目的材料处理摘要中；
- 缺少可靠正文、模型调用持续失败或输出合同持续无效等运行条件失效进入“需要处理”并阻塞阶段交接；人工模式中，两次自动修订仍未通过也保留给用户处理；
- 尚未完成的材料表示本阶段仍在运行。

“需要处理”只表示系统无法继续读取或执行，不用于承接自动模式下的普通 Review 意见。用户可在该阶段看到真实故障原因；正常的内容判断、修订、复审和不入选结论都由后台完成。自动模式在零份材料通过 Review 时停止，因为此时已经没有可进入主题组织的有效材料；不得另设“至少 N 份”之类机械阈值。

当所有材料都已通过或明确不入选后，系统自动开始准备下一阶段的主题方案和讲义小样。人工模式不会未经第二次确认直接批量编写完整讲义；自动模式已经在第一次确认取得继续成书的明确授权。

### 第 2 阶段：确定知识应该怎么组织

系统先让并发助手根据已经通过 review 的笔记提出候选主题、证据范围、冲突和遗漏清单，再由总编模型统一决定主题划分、讲义组织方式和导航思路。总编随后选择 1～2 个代表性主题并说明选择理由，生成讲义小样；Reviewer 完成检查，总编根据具体意见做必要修订。

如果全部通过的笔记能够被总编模型一次完整读取，主题规划可以一次完成。如果不能，系统必须先按明确、有意义的范围形成规划批次，例如同一老师、同一来源系列或笔记中已经标明的候选主题。每个批次完整读取其范围内的笔记，由助手提出候选主题并保留对应的笔记和来源映射；总编再根据这些候选主题和映射形成项目级主题方案和当前编辑方案。

候选主题的合并也遵守同一条完整输入原则。如果一轮产生的候选主题和映射仍然无法一次完整读取，就继续按已有的明确范围递进归并，并始终保留主题到原笔记和来源的映射。任何一层都不能静默截断、只取前一部分，或用脱离来源的短摘要替代必要输入。

这种分批不是按 token、文件顺序或固定数量随意切开，也不能只取前一部分笔记。如果系统无法形成既有意义、又能让模型完整读取的规划范围，就进入“需要处理”，让用户缩小项目范围、调整分组或拆分项目。

第 2 阶段的可见产物包括：

- 主题和讲义规划；
- 主题之间的关系和覆盖范围；
- 1～2 篇讲义小样；
- 小样对应的 review 结果。

人工模式再次停下来，让用户确认：

> 这样组织和表达已经学到的知识，对不对？

如果不对，调整主题方案、编辑方案或讲义写法并重新生成小样；如果确认，主题地图、当前编辑方案和讲义小样共同固定为本轮组织版本，进入批量讲义编写。

这是人工模式的第二个、也是批量编译前最后一个确认点。自动模式不显示这次确认：讲义小样通过后，系统固定当前主题地图和编辑方案并继续成书。若总编把全部通过笔记都明确列入 `unassigned_notes`，项目以“有效材料不足以形成可信 Skill”的具体原因停止；部分未分配笔记按模型理由记为不入选，其余主题继续。代码不按笔记数量猜测可信度。

### 第 3 阶段：批量编讲义并形成 Skill

第 3 阶段不是第 1 阶段的并发复刻。系统可以按主题并发准备证据包、冲突清单和遗漏检查，但讲义正文、关键修订和最终版本由总编模型依照已确认的编辑方案负责。

每篇讲义遵循受控闭环：

```text
助手准备当前主题的证据包和问题清单
-> 总编模型形成讲义正式候选稿
-> Reviewer 给出具体问题
-> 总编只针对这些问题修订
-> 通过，或进入需要处理
```

Reviewer 不直接改稿，多个 Agent 不轮流重写同一篇讲义，也不因为“也许还能更好”而无限循环。人工模式在自动修订达到上限后保留当前稿和具体原因，交给用户处理。自动模式同样保持有限修订；若模型在预算内始终无法交付通过 Review 的阶段产物，按当前模型或输出合同无法继续的运行条件失效停止，不静默接受，也不无限重试。

全部讲义稳定后，总编模型执行一次全书收口，检查术语、主题边界、多老师观点、重复和缺口，以及讲义、导航、证据和回答方式之间的一致性，再生成导航和最终 `SKILL.md`。如果全书输入不能一次完整读取，同样按已有主题结构递进检查和归并问题，不能截断或只读部分讲义。

讲义完成后，系统继续完成导航、检索资料、来源清单和最终 `SKILL.md` 的组装，并检查这些产物是否能够被当前 Skill 运行方式正常读取。

最终成品先供用户预览，不自动启用。用户确认成品可用后，手动启用专家 Skill。

最终交付保持为普通、独立的 Skill：

```text
skill/<name>-expert/
  SKILL.md
  nav/
  references/
  wiki/
  search/
  sources.jsonl
```

原始上传文件和整份可靠正文、项目 Prompt、review 记录、失败信息、任务清单和项目进度都属于编译过程，不发布到最终 Skill 中。

最终 Skill 的 `wiki/` 保存通过 Review 的正式讲义；`references/` 是运行时证据层，保存从已入选材料中筛选出的、足以支撑讲义关键判断的引用片段和必要上下文，而不是整份原始上传文件，也不是脱离原文的二次摘要。讲义中只对会改变读者判断的关键结论保留证据引用，不建立逐句审计台账。

模型在当前任务中只使用系统提供的材料别名和行号描述证据，不生成数据库 ID、正式路径或来源清单。Yuxi 负责把这些任务内引用映射为正式 `references/` 文件和 `sources.jsonl`：每条证据包含来源标题、作者或说话人、可用的位置描述、必要上下文，以及它所支撑的讲义和判断。无法定位必要证据的关键结论不能通过讲义 Review。

运行时只读取最终 Skill 内的讲义、导航和精选证据，不另开一条访问项目内部原始材料的路径。这样最终 Skill 既能独立使用和核对依据，也不会把整个材料包作为发布物带出去。

## 用户真正需要看到的状态

流程内部会有许多材料和讲义任务，但页面不应该把每一个内部动作都变成一个大的项目状态。

人工模式主要看到：

```text
准备学习
-> 等待确认
-> 批量学材料
-> 等待确认
-> 批量编讲义
-> 成品待启用 / 需要处理
```

自动模式在第一次等待确认时显示自动推进的范围和后果；确认后连续展示当前真实阶段：

```text
准备学习
-> 等待确认并选择自动推进
-> 方法校准 / 批量学材料 / 组织主题 / 批量编讲义
-> 成品待启用 / 需要处理
```

笔记撰写、笔记 review、修订、单份失败、讲义 review 等都属于当前阶段内部的信息。用户需要时可以查看明细，但不应被迫理解一条冗长的工程状态机。

“需要处理”必须给出具体、可行动的原因，例如某份材料无法转成正文、超过上下文范围、模型调用失败、输出格式错误、模型在有限修订内仍无法交付阶段合同，或者有效材料已经不足以形成可信 Skill。不能只显示一个笼统的失败状态，也不能静默接受未通过的内容。人工模式仍等待用户处理；自动模式只在这些运行或材料事实已经无法继续时停止。

## 项目记录、后台队列和任务中心的职责

三者各自解决不同的问题，不能混为一体。

### 项目记录是事实来源

项目自身必须记住：

- 当前做到哪个阶段；
- 当前是否在等待用户确认；
- 第一次方法确认是否授权自动推进；
- 哪些材料已经处理、通过、跳过或卡住；
- 每份材料和每篇讲义的产物在哪里；
- 失败原因和已经尝试的次数；
- 服务恢复后下一步应该做什么。

即使后台服务重启、队列任务消失或任务中心刷新，这些事实也不能丢失。系统应能根据项目记录继续未完成工作，并跳过已经完成且产物有效的任务。

这里的“产物有效”只表示：产物存在、能够解析，并满足当前输出合同的必填字段和引用关系。它不要求 hash、任务指纹、Prompt 指纹、审计链或历史证明。

### 后台队列负责干活

后台队列负责领取任务、控制并发、调用普通模型或 Prime、保存结果和报告执行状态。当前项目使用 ARQ 承担这类跨进程执行。它不是项目历史，也不是项目是否完成的最终判断依据。

大批材料进入后，可以同时运行多份独立的材料任务；进入编辑阶段后，可以并发准备多个主题的证据包、候选和 review。会更新编辑方案、正式讲义或最终 Skill 的总编任务在同一项目内保持串行。并发的目的是提高研究吞吐，不能把最终作者性拆散。

### 任务中心负责展示

任务中心是用户查看当前运行情况的看板，展示总体进度、正在进行的工作和失败摘要。它不承担项目恢复，也不能成为每份材料结果的唯一存放位置。API 进程内的 Tasker 不负责恢复专家项目，也不能据此判断项目的真实阶段；服务恢复时，应读取专家项目记录并重新投递尚未完成的 ARQ 工作。

项目记录回答“事情实际做到哪里”；后台队列回答“现在谁在执行”；任务中心回答“用户现在看到什么”。

## 普通模型任务的共同约定

逐份材料学习、局部 review、证据准备和检查等普通模型任务，都是一次独立、无状态的调用。

系统负责在调用前组装：

- 专家作品身份与编辑使命，让模型理解自己正在继承和编写怎样的领域判断手艺；
- 当前阶段对应的角色和行为边界；
- 已确认的项目学习方案；
- 当前任务的明确说明；
- 当前任务真正需要的完整材料或上游产物；
- 输出格式和 review 标准。

专家作品身份不是泛泛的角色扮演。它说明最终成品应成为一位有明确判断传统、能解释条件与边界的领域专家；项目学习方案再决定当前项目的具体领域、材料读法、专家口吻和真实风险停止线。学徒、Reviewer 与总编共享这一使命，只是在当前阶段分别承担学习、守证据或统一编辑的职责。

模型上下文只包含当前职责所需的业务语义。任务 ID、版本、存储位置、输出路径、文件名、哈希、队列状态、尝试次数、目录布局和发布清单由系统保存与补充，不要求模型阅读或输出。

项目专属 Prompt、任务响应合同和系统记录是三层不同的东西：

- 项目专属 Prompt 说明当前领域的角色身份、判断方法、材料边界和写作方式；
- 任务响应合同只承接模型必须做出的业务判断，例如材料是“可用、没有迁移价值还是需要处理”，Review 是“通过、修订还是需要处理”，以及具体问题、判断和不确定性；
- 系统记录保存任务、材料、版本、路径、尝试次数、队列状态和正式产物关系。

任务响应合同可以由调用层用结构化响应约束实现，但不应把任务 ID、路径或其他机器记录重新塞进模型 Prompt。没有这些业务结论，系统无法可靠决定继续、修订、排除还是停下来等待用户处理。

这些普通模型任务不负责：

- 自己扫描项目目录；
- 自己决定应该读取哪些文件；
- 依赖上一轮对话记住上下文；
- 自己推进项目到下一阶段；
- 自己把结果写到任意位置。

系统拿到返回结果后做必要的机械检查并保存。机械检查只保证结果可被系统继续使用，例如：

- 是否有结果；
- JSON 或 Markdown 是否能够读取；
- 下游必需字段是否齐全且类型正确；
- 产物是否属于当前项目和当前任务。

机械规则不判断内容质量。不能用字数、标题数量、关键词数量等规则假装判断笔记或讲义是否优秀。内容是否学对、写对，由相应的 review 模型判断；人工模式由两个确认点决定整体方向，自动模式由第一次确认同时授权后续模型在既定方法、Review 和总编边界内完成取舍与成书。

第一版的总编模型同样是受控的无状态任务：系统显式提供当前编辑方案、当前主题的完整证据、当前稿和具体 Review 问题；同一项目内总编写入保持串行。未来 Prime 接入时，它可以在项目工作台内主动阅读、分析、编辑、缓存和运行系统提供的校验工具，但这个增强只改变总编完成工作的方式，不改变 Yuxi 对输入范围、正式状态、候选提交和发布的控制。

## 后续增强：Prime 总编工作台

每个专家项目拥有独立的 Prime 工作台。它是总编处理资料、稿件和自检结果的编辑空间，不是项目正式记录，也不是最终发布目录。

工作台在概念上分为三部分：

```text
输入区
- 当前任务说明
- 当前项目和编辑方案版本
- Yuxi 授权提供的材料、笔记、证据和已确认产物

工作区
- 草稿、分析结果和中间文件
- Python 或 iPython 处理结果
- 当前项目可复用的编辑缓存
- 自检报告

候选区
- 待提交的编辑方案更新
- 待提交的讲义、导航和 SKILL.md
- 候选产物清单和自检结果
```

输入区由 Yuxi 准备，Prime 只读取当前任务明确授权的项目资料；工作区允许 Prime 自由读写、使用文件和 Python 工具，并在同一项目后续总编任务中复用缓存；候选区保存本轮准备提交的结果。Prime 不能直接写项目正式记录、正式产物或已启用 Skill。

工作缓存用于减少重复阅读和支持编辑过程，丢失后只影响效率，不能影响项目恢复。项目学习方案、编辑方案、正式笔记、正式讲义和来源映射仍由 Yuxi 持久化。每次总编任务必须以 Yuxi 提供的当前版本和任务清单为准，不能因为工作台残留旧稿就覆盖较新的正式决定。

### Prime 的自主编辑闭环

Prime 可以在一次总编任务内部完成：

```text
读取任务和授权输入
-> 分析并写作候选稿
-> 运行系统提供的校验工具
-> 根据具体错误自主修订
-> 再次校验
-> 提交候选产物和自检报告
```

系统可以提供确定性的项目校验工具，例如检查输出结构、来源映射、主题冲突、导航目标和 Skill 是否可加载。Prime 的自检是写作过程的一部分，不取代 Yuxi 的最终门禁，也不能使用字数、关键词等机械规则冒充内容质量评价。

Prime 的内部迭代同样有明确预算，包括最大运行时间和最大自检或修订次数。达到上限仍不能提交合格候选时，保留当前稿、自检报告和失败原因，项目进入“需要处理”。

### Yuxi 的正式门禁

Prime 提交的始终是候选结果。Yuxi 在提交后独立执行同一套必要校验，并确认：

- 候选结果属于当前项目和当前任务；
- 项目版本和编辑方案版本没有在执行期间变化；
- 预期文件存在、可解析且必填关系齐全；
- 来源引用只指向当前项目授权的证据；
- 主题、讲义、导航、来源映射和 Skill 目录能够互相对应；
- 输入材料、工作缓存和自检过程文件没有混入发布物。

校验通过后，Yuxi 才把候选结果原子写入项目正式产物。校验失败时，把具体问题交还 Prime 做有限修订；多次仍不合格则进入人工处理。Prime 不直接修改项目阶段，不直接覆盖正式成品，也不直接启用 Skill。

### Prime 接入时必须具备的隔离

Prime 可以在项目工作台内自由使用工具，但“当前工作目录”本身不是权限边界。上传材料即使来自内部，也可能包含影响 Agent 行为的指令，因此 Prime 接入时必须先具备轻量、真实的运行隔离，不能以验证产品价值为由跳过。

最低边界是：

- 每个专家项目使用独立工作台，不能混用其他项目缓存；
- Prime 只获得当前项目授权资料，不直接查询 Yuxi 数据库；
- Prime 不能访问其他项目、系统凭证、宿主目录或 Docker 控制接口；
- Prime 不能看到或修改正式发布目录；
- 运行环境使用非特权身份，并限制运行时间、资源和子进程范围；
- 网络默认不作为总编工作的必要能力，确有明确任务时再单独讨论开放范围。

这些边界不限制 Prime 在工作台内使用文件、Python、搜索和校验工具。它们只是把“自由工作”限定在当前项目明确授权的范围内。具体采用独立容器、沙箱服务还是现有运行后端，在实施设计中决定。

## 后续增强：Prime 高级问答模式

Prime 除了作为编译时总编，还可以成为用户在网页端主动选择的高级问答模式。它适合需要跨多篇讲义和证据进行比较、推演和综合判断的问题；普通 Agent 仍承担更快的一般问答。

两种用途共享 Prime 运行基础和已发布 Skill，但必须保持数据边界：

| 模式 | 可见内容 | 结果 |
| --- | --- | --- |
| Prime 总编 | 当前项目授权的材料、笔记、草稿和编辑工作台 | 候选学习方案、讲义、导航和 Skill |
| Prime 高级问答 | 用户有权使用的已启用 Skill | 对话答案和本次问答临时分析 |

高级问答 Prime 不得访问编译中的项目工作台、未确认稿件或内部 review 结果。它可以为当前问答保留独立缓存，但不能把该缓存写回编译项目，也不能改变已发布 Skill。产品上应明确它比普通问答更慢、资源消耗更高，适用于复杂问题。

## 模板、学习方案和 Prompt 的关系

为了避免后续讨论混淆，这三个概念约定如下：

- 模板：面向某一类材料的通用学艺方法，只用于开启新项目；
- 项目学习方案：模板经过当前材料探测后形成的、人可以阅读和确认的项目专属方法；
- Prompt：系统为了某个具体模型任务，把项目学习方案、任务要求、输入内容和输出约定组装成的实际调用上下文。

UI 默认向用户展示项目学习方案和小样，而不是要求用户阅读底层 Prompt。原始 Prompt 可以展开查看，主要用于高级检查和排查。

用户确认的是“怎么学”和“怎么组织”，不是某个难以阅读的字符串版本。自动模式把“怎么组织”的后续取舍授权给已经确认的方法、Review 和总编流程；人工模式仍由用户第二次确认。

## 必须保留的底线

后续实现不得偏离以下原则：

1. 第一版不接入 Pi 或 Prime；复用 Yuxi 自己的模型调用和后台执行能力完整跑通专家学习与编译主链。
2. 不把整个材料包一次交给一个模型；每个任务只接收它需要的完整输入。
3. 第一版的模型任务不自己找文件、猜上下文或依赖多轮会话；未来 Prime 只能在 Yuxi 准备的项目工作台内主动工作。
4. 原始二进制文件先转成可靠正文，再进入模型学习。
5. 超长材料不静默截断，先形成有意义的材料单元。
6. 第 0 阶段确认“怎么学”始终必需；人工模式还在第 2 阶段确认“怎么组织”，自动模式必须由用户在第一次确认时明确开启，不能由模板、后台或历史默认值代替授权。
7. 第一阶段结束后自动准备主题方案和小样；人工模式等待第二次确认后再批量写讲义，自动模式在小样通过后继续成书。
8. 人工模式中“需要处理”的材料必须经过用户明确处理或排除；自动模式中内容采用、有限修订后的取舍和排除由模型决定，只有运行条件失效或有效材料不足才停止。
9. 主题规划同样不能静默截断或暗中抽样；超出上下文时按有意义范围规划，无法形成范围时停下处理。
10. 普通助手并行研究，项目内串行的总编模型决定主题结构、讲义正式稿和最终回答口径；未来 Prime 只替换总编执行者。
11. 总编连续性来自当前有效的编辑方案和正式产物，不依赖长会话记忆。
12. 第一版总编由系统显式提供完整上下文并提交候选结果；Yuxi 独立校验并原子晋升，同一项目的总编编辑写入保持单一写入者。
13. 上传材料始终按不可信输入对待；未来 Prime 接入时必须在不含其他项目、系统凭证、Docker 控制接口和正式发布目录的隔离范围内运行。
15. 项目记录是唯一的进度事实来源；ARQ 负责执行；任务中心负责展示；API 进程内 Tasker 不负责恢复。
16. 页面状态保持简单，具体 review、修订和失败保留在阶段内部。
17. 格式由机械规则检查，内容质量由 review 判断，不用字数和关键词规则冒充质量评价。
18. 自动重试和修订必须有限；运行或阶段合同在预算内仍无法成立时给出明确原因并停止，不无限重试或静默接受。
19. 中央模板的修改只影响新项目，不影响已确认项目。
20. 最终 Skill 只包含运行所需成品和可核对的精选证据，不夹带工厂过程材料或整份原始正文。
21. 运行时只读取最终 Skill，不绕过 Skill 边界访问项目内部原始材料。
22. Prime 高级问答属于后续里程碑，只读取用户有权使用的已启用 Skill，不读取总编工作台或编译中内容。
23. 不引入审计账本、hash 链、全图 DAG、复杂 redo、运行回执或多宿主调度。

## 这次不做什么

本次改造不以恢复或增强旧知识库、向量数据库和知识图谱链路为目标，也不把专家学习流程重新包装成传统文档分块入库。

以下能力不属于当前目标：

- Pi 或其他外部批量执行宿主；
- 盲测、holdout、三臂评测和效果实验平台；
- 多套运行 profile 和复杂发布治理；
- Prompt、任务、消息和输出的 hash 证明；
- dispatch log、receipt、reservation 和完整执行历史；
- 通用 DAG 编排器和任意流程设计器；
- 为了可追溯而复制所有输入和中间档案；
- 用大量规则替代模型 review 的内容判断。

以后如果出现明确、真实的需要，可以单独讨论；不能以“未来可能有用”为理由提前放进这次主流程。

## 成功时用户会经历什么

一个用户创建专家项目并导入材料。系统先把文件转成可读正文，由总编模型针对这批材料形成学习方案、项目方法版本和少量笔记小样。用户确认方向时选择人工模式或自动推进；系统随后在后台并发学习所有材料，并持续显示真实总体进度和停止原因。

人工模式中，如果有材料无法自动完成，系统不会悄悄跳过，而是在阶段交接时让用户修复后重跑、明确排除或暂停项目；总编形成统一主题地图、编辑方案和少量讲义小样后，再次请用户确认组织方式。自动模式中，普通内容问题由模型继续修订或明确记为不入选；只有运行条件失效、零份材料通过 Review，或全部通过笔记被总编明确列为未分配时停止。

人工模式在第二次确认后、自动模式在讲义小样通过后，由助手并发准备各主题证据和 review，总编模型以显式上下文逐篇定稿和修订，并最终完成全书一致性、导航和 Skill 收口。提交的仍是候选成品；Yuxi 独立校验通过后才写入正式项目产物。任何模式都不自动启用 Skill。未来 Prime 接入后，可以在不改变这条主链的前提下增强总编的工作台和自检能力。

用户预览成品和未纳入材料清单，手动启用。之后 Agent 可以通过这个 Skill 找到相关方法、讲义和带来源标识的精选证据，结合可核对的依据回答实际问题。

人工模式让用户在“怎么学”和“怎么组织”两个位置定方向；自动模式只在第一次确认时授权系统推进到候选成品。两种模式都不要求用户理解内部队列或逐份批准重复劳动。

## 验收标准

1. 支持的原始文件能够先转换为可靠正文；不能处理的文件会明确说明原因，不进入学习阶段。
2. 第 0 阶段能产生项目专属学习方案、完整项目方法版本、笔记小样和 review，并等待用户确认。
3. 用户确认后，项目学习方案、编译底稿和完整阶段 Prompt 包一起固定在项目中；中央模板变化不会影响该项目。用户反馈或重新定向导致的语义 Prompt 修改必须生成新方法版本并重新确认；自动模式明确授权的有限方法校准可以生成和试跑 V2，不增加人工确认。
4. 每份材料由独立任务处理，调用中包含该任务所需的完整材料和上下文。
5. 多份材料可以并发执行；单份失败不会导致已经完成的材料重跑。
6. 笔记能够自动 review，并在有具体意见时持续定点修订和复核至明确结论。
7. 没有迁移价值的材料可以正常跳过，不进入主题和讲义。
8. 缺少可靠正文、模型调用持续失败或输出合同持续无效会明确阻塞阶段交接；人工模式保留有限修订后人工处理，自动模式由模型最终判定采用或 `no_value`。
9. Reviewer 明确判定不入选的材料会出现在主题方案和成品预览的未纳入清单中。
10. 第一阶段结束后，系统自动生成主题方案和讲义小样；人工模式停在第二个确认点，自动模式在小样通过后固定组织版本并继续成书。
11. 主题规划输入超出上下文时按有意义范围形成规划批次，不会静默截断、暗中抽样或只取前一部分；无法形成合理范围时会停止并提示用户处理。
12. 人工模式未经第二次确认不会批量生成完整讲义；自动模式只有在用户第一次确认时提交 `auto_advance=true` 才能跳过该确认。历史项目和旧 API 默认关闭自动推进，新页面开关默认开启。
13. 候选主题、证据包、冲突和遗漏检查能够并发准备，但主题地图、编辑方案、讲义正式稿和最终 Skill 由项目内串行的总编模型统一决定。
14. 同一项目内更新编辑方案或正式稿件的总编任务保持单一写入者；服务重启后可根据正式编辑方案继续。
15. 总编模型只接收当前工作真正需要的完整上下文；Yuxi 独立检查项目版本、文件结构、引用范围和 Skill 可加载性，再原子写入正式产物。
16. 全部讲义完成后，总编模型会检查术语、冲突、重复、缺口、导航和回答口径的一致性，再生成最终 Skill。
17. 讲义中会改变读者判断的关键结论都能关联到任务内材料别名和位置；Yuxi 据此生成精选证据与来源映射，无法定位必要证据的结论不能通过 Review。
18. Prime 高级问答属于后续里程碑，只能读取用户有权使用的已启用 Skill，并与编译中内容隔离。
19. 服务或 Worker 重启后，项目仍能知道做到哪里，并只继续未完成或不满足输出合同的任务。
20. 任务中心能够展示进度，但项目恢复不依赖任务中心或 API 进程内 Tasker 的临时运行记录。
21. 输出只做必要的结构检查，内容质量由 review、总编和当前确认模式判断；任务响应合同提供继续、修订、排除或需要处理所需的业务结论，机器记录由系统保存。
22. 超出模型上下文的材料不会被静默截断；无法形成自然材料单元或有意义规划批次时进入“需要处理”。
23. 最终发布物不包含整份原始上传文件或可靠正文、项目 Prompt、review、失败记录或任务进度。
24. 最终 Skill 的 `references/` 包含带来源标识、足以支撑讲义判断的精选证据，`sources.jsonl` 保存来源和引用映射。
25. 最终 Skill 由用户手动启用；自动推进最多到候选成品，不得调用启用。启用后能够被当前 Agent 独立检索和阅读，不访问项目内部原始材料。
26. 自动模式只在运行条件失效、零份材料通过 Review，或总编将全部通过笔记明确列为未分配等无法形成可信 Skill 的事实出现时停止；不能使用材料数量阈值或无限重试。

## 第一版真实验证材料与放量方式

第一版以本机现有的杨炎四柱材料包验证完整主链：

```text
/Users/will/ai-workspace/wiki-source/final/bilibili/杨炎四柱解惑
```

该目录当前包含 224 篇 Markdown 文章。它是开发和验收使用的外部真实语料，不复制进本仓库，也不作为最终 Skill 发布物的一部分。

每一篇文章是一个自然材料单元，也是第 1 阶段的一个独立学习任务。系统不能把一篇文章按字符数拆成多个并发任务，也不能把 50 篇文章合并成一个任务。文章标题、来源和完整正文由系统作为该任务的完整输入提供给模型。

验证必须渐进放量，不以一次性全量运行作为第一步：

1. 先使用 `0001-有大财的姐.md` 跑通项目定向、项目方法版本、小样确认后的单篇学习、Review、自动修订、产物保存和项目恢复。若第 0 阶段的小样正好就是这篇文章，只有它使用相同项目方法版本并完成相同响应合同后才可提升为正式结果；否则必须按第 1 阶段重新处理，不能因为看过样本就跳过。
2. 再使用排序后的前 5 篇文章验证五个独立任务的并发、单篇失败或修订不影响其他文章、进度展示、断点恢复和第一阶段交接判断。
3. 在前两步均稳定后，对整个材料包执行第 1 阶段全量验证。只有每篇文章都已通过或明确不入选，系统才自动开始第 2 阶段的主题方案和讲义小样准备；存在无法读取或持续执行失败的文章时必须停在阶段交接页。

默认并发数为 50，含义是 50 个持续补位的任务槽位，而不是固定大小的批次：

```text
有 224 篇待处理文章
-> 立即启动前 50 个符合执行条件的文章任务
-> 任一任务到达终态
-> 立即从剩余待处理文章中补入下一个任务
-> 始终尽量维持 50 个运行槽位
-> 直到没有可执行文章
```

终态包括通过、明确不入选、需要处理和达到有限重试上限后的运行失败。终态任务释放槽位；“需要处理”不会阻塞其他文章继续完成，但会阻塞第一阶段向第二阶段正式交接。自动模式中的普通内容问题由模型判定采用或不入选，不转成逐项人工处理。并发数小于待处理文章数时，系统始终补满可用槽位；待处理文章不足 50 时，启动全部剩余文章。

这里的 50 是项目学习任务的并发槽位目标。实现时必须同时尊重模型供应商的实际限流、系统资源和可用 Worker 容量；遇到可识别的限流或临时调用失败，应按有限重试和退避处理，但不能退化为“等第一批 50 个全部结束后才派下一批”的批处理语义。

## 产品命名与文档方向

这次改造不是在原有知识库产品旁边增加一个专家编译功能，而是在形成一条新的产品主线。新产品暂定名称为：

```text
知铸 ZhiForge
```

“知铸”表达的是把可靠材料中的判断、条件、经验和手艺，经过学习、Review 和总编收口，铸造成可以启用、检索和实际回答问题的专家 Skill。后续产品说明不应再把它概括为以知识库、向量检索或知识图谱为中心的平台。

面向用户的统一产品叙事应是：

> 知铸将一批可靠材料学习为具有统一判断、可核对依据和清晰导航的专家 Skill；普通助手并行扩大材料覆盖面，项目内串行的总编模型负责学习方案、主题结构、讲义作者性和最终收口，用户在关键确认点决定方向。Prime 总编和 Prime 高级问答属于后续增强能力，不阻塞第一版主链。

- 与发布相关的 changelog、新版本说明和迁移说明。

这些文档需要共同表达以下变化：

- 主流程是“材料转正文 -> 确认怎么学并选择推进模式 -> 批量学习 -> 人工确认或自动组织 -> 总编成书 -> 预览并手动启用”；
- 第一版由总编模型完成学习方案、主题结构、讲义作者性和最终收口，普通模型任务负责并行阅读、Review 和证据准备；Prime 是后续可选的总编与高级问答增强；
- 项目记录是流程事实来源，ARQ 负责执行，任务中心负责展示；
- 最终运行时读取已发布 Skill 中的讲义、导航和精选证据，不依赖旧知识库、Milvus 或 Neo4j 主链路；
- 旧专家 Skill 在过渡期继续可用，新项目进入新的专家学习流程。

文档修订不是简单做字符串替换。已经失效的旧流程说明应删除或明确归入兼容模式；仍然有效的底层能力应按新产品中的职责重新解释。历史 changelog、历史版本说明和引用旧项目名称的事实记录不回写，以免改写历史。

### 本轮命名边界

本轮只冻结新产品名称和后续文档迁移要求，不立即执行全仓改名。面向用户的产品名称后续统一使用“知铸”或“ZhiForge”；仓库目录、Python 包 `yuxi`、`YUXI_*` 环境变量、API 路径、数据库标识和其他技术名称暂时保留。

技术标识是否改名应在产品主流程稳定后单独评估兼容成本，并制定明确迁移方案。不能在专家学习改造中顺手进行无边界的全仓重命名，也不能因为内部仍保留 `yuxi` 标识，就继续在用户文档中沿用旧品牌和旧产品定位。

## 与已有文档的关系

`docs/vibe/2026-08-17-expert-skill-engine.md` 记录的是专家 Skill 引擎第一阶段，主要解决运行模式、材料包上传、快速索引、Skill 激活和 Agent 消费。

本文记录的是下一阶段的大改造：在现有产品边界内，把简单整理编译升级为真正的专家学习流程。第一阶段已建立的上传、后台运行、Skill 安装、启用和检索能力应尽量复用；其中简单编译和单次生成 `method.md` 的方式，不代表本文目标中的最终学习流程。

当前 `run_prime_acp` 和 `compile_expert_package_with_prime` 只证明 Yuxi 可以启动 Prime、交付一次任务并收回结果，是后续总编运行基础的起点。现有调用直接在 Worker 可见目录中运行，并以一段返回文本生成 `method.md`，尚不具备本文要求的项目工作台、编辑方案、候选提交、独立门禁、单一写入者、完整取消超时和运行隔离。因此不能把现有函数直接扩张为整套总编流程，也不能把当前 Full Access 运行方式视为已经满足本文边界。

过渡期间，已经启用的旧专家 Skill 继续可用，不自动迁移、不自动覆盖。新导入的专家项目全部进入本文定义的新流程；旧专家包需要升级时，由用户主动发起重新编译。在新流程成功生成并由用户启用成品前，原有已启用 Skill 不受影响。

## 最后一条判断标准

每准备增加一个机制，都先回答：

> 不加它，会让哪一个已经确认的用户流程无法成立？

如果说不出具体失败点，就不把它加入这次改造。
