# 资料库作为专家材料前置底座：实施说明

日期：2026-08-19

状态：Owner 已确认主流程与已有项目过渡方式，实施中。资料库所有权与可见范围仍按下文待确认项处理。

## 目标

恢复用户熟悉的上传、目录管理、处理进度和失败重试体验，但上传目标直接改为新的独立资料库，不恢复旧知识库入库链路。用户先在资料库批量导入和管理材料，系统完成 OCR、解析和现有解析器已提供的确定性格式归一化，保存可核对的完整正文；长书和长材料再形成可供专家项目选择的自然主题材料单元。新增专家项目只选择已处理完成的材料单元进入第 0 阶段及后续学习，不在项目内再次上传同一份文件。

这条流程要解决两个已经存在的实际问题：专家项目现在在创建时直接上传原始文件，并把正文复制到项目私有目录；长书如果直接作为一份材料进入模型，既可能超过上下文，也无法保证后续学习对应的是完整、有意义的内容范围。资料库把文件处理与专家学习分开，专家项目只接收已经可读、边界明确且能回到来源位置的材料单元。

最终主流程如下：

```text
批量上传与目录整理
-> OCR / 解析 / 确定性格式归一化，得到完整可靠正文
-> 按原有书籍结构做粗粒度范围
-> 模型确认或调整自然主题边界
-> 已处理材料单元
-> 用户选择材料单元创建专家项目
-> 第 0 阶段及后续专家学习与编译
```

## 非目标

- 不把固定字符数、固定 token 数、正则猜测内容或按文件位置采样当作材料单元的边界判断。
- 不把旧 `KnowledgeChunk` 作为专家学习单元，也不让整本书直接进入后续逐份学习任务。
- 默认不调用 embedding、Milvus、向量入库、召回或 Neo4j 图谱。它们继续是传统检索的显式兼容能力。
- 不在本轮增加新的自动确认点、复杂 DAG、审计链、通用编排平台或 API 进程内恢复机制。
- 不改变人工模式的两个专家项目确认点：第 0 阶段确认“怎么学”，第 2 阶段确认“怎么组织”。资料库中的单元准备不替代它们；自动模式只在用户于第一次确认时明确开启后，按下文授权继续到候选 Skill。
- 不发布资料库中的整份原始文件、完整正文、章节化过程或失败记录；最终 Skill 的发布边界仍以现有专家主线为准。

## 已确认的迁移口径

- 恢复的是旧版用户熟悉的上传和目录管理入口及交互，不恢复旧知识库的数据模型、分块、向量入库、图谱或非 LITE 运行链路。
- 上传文件直接进入新的独立资料库。资料库是新增材料的唯一入口和唯一正文事实来源。
- 新增专家项目只能选择资料库中已经处理完成的材料单元，不提供项目内上传、替换或追加材料入口。
- 已经直接上传材料的旧专家项目继续从现有项目记录和项目私有材料中兼容读取、恢复和完成原流程；兼容能力不把旧项目迁回资料库，也不为旧项目恢复新增、替换或再次上传控件。
- 上述新流程必须在默认 `LITE_MODE=true` 下可用；旧知识库只保留传统检索兼容能力，不成为资料库或新增专家项目的运行依赖。

## 自动推进与人工模式

第一次展示项目学习方法和真实小样时，页面提供“自动推进”开关。新页面默认开启，但只有用户确认时提交的 `auto_advance` 才成为项目事实；数据库字段和旧 API 请求默认关闭，因此历史项目、升级前项目和未发送该字段的调用方继续走人工流程，不会被追溯推进。

人工模式保持现有流程：方法校准并复跑 V2 小样后再次等待用户确认；材料出现需要处理时由用户重跑或明确排除；主题地图、编辑方案和讲义小样完成后等待第二次确认；正式讲义或全书收口失败时由用户显式重跑。

自动模式中，第一次方法与小样确认是候选 Skill 成书前最后一次人工确认。系统随后自动完成方法校准和小样复跑、逐份学习与 Review、材料定点修订或模型排除、主题组织、讲义编写与 Review、有限修订、全书收口和候选 Skill 组装，不再等待方法 V2 或组织方式确认。自动模式永不自动启用 Skill；候选成品仍停在预览页，由用户手动启用。

自动模式不把内容质量问题交给机械规则或用户逐项处理。材料经过有限修订后，最终由模型判定采用或记为 `no_value`；总编可以用现有未分配笔记事实明确不采用已审笔记。代码只保存这些结论并推进确定性状态。只有运行条件失效，或模型排除后零份材料通过 Review、全部通过笔记都被总编明确列为未分配等事实表明无法形成可信 Skill 时，项目才停止并给出具体原因。不得增加材料数量阈值、无限重试或另一套自动流程状态机。

## 当前实现与复用边界

当前旧知识库已具备文件夹层级、批量上传、文件状态、失败原因、全文解析和正文保存能力。`KnowledgeFile` 已保存父目录、状态、错误信息和 Markdown 路径；`yuxi.knowledge.parser` 与 `yuxi.services.ocr_service.parse_document` 已承担 OCR 和文档转 Markdown。本方案复用这些入口、交互和通用解析能力，但新的资料库事实不依赖 `KnowledgeFile`、旧知识库外键或旧入库流程。资料入库时先完成解析、清洗和确定性格式归一化，再保存规范化 Markdown；本文所说的格式归一化不新增模型判断或独立用户状态。规范化正文保存后，`line_count`、模型输入中的 `L<n>` 行号和后续证据行号都以这份正文为准。

同一条旧链路中的 `KnowledgeChunk`、`MilvusKB`、分块器、embedding、图谱抽取和 RAG 查询不属于默认专家材料链路。资料库准备完成后，专家项目读取的是完整的材料单元及其来源定位，不读取 RAG chunk，不等待向量或图谱任务完成。

当前专家项目在 `create_expert_project` 中接收上传文件，并由 `expert.storage` 写入项目私有 `raw/` 与 `text/` 目录。`ExpertMaterial` 也把原始文件和正文路径作为项目内事实保存。实施时要把“直接上传并转换”替换为“从资料库选择就绪单元并建立项目材料关联”；专家项目不再保存第二份原始文件或完整正文。第 0 至第 3 阶段的学习、Review、总编和发布边界保持不变。

当前前端已经有专家项目列表、详情、人工模式的两次确认、材料问题处理、候选 Skill 预览与手动启用页面。阶段 C 只改造列表页和创建接口的材料来源，从多文件上传改为选择资料库就绪单元；项目详情页的定向、确认、Review、预览和启用交互应继续复用。自动推进开关也放在第一次方法与小样确认处，不另做设置页或另一套专家项目页面。

当前 `expert.worker` 与 `run_worker` 已在 ARQ 中登记专家任务，并在 Worker 启动时从 PostgreSQL 的项目事实重投未完成工作。`expert.task_view` 已把项目事实投影给任务中心。资料库的处理和章节化应沿用同一原则：状态、错误和结果落在 PostgreSQL；ARQ 只负责执行与恢复投递；任务中心只展示进度，不承担恢复。

资料库必须在默认 `LITE_MODE=true` 下可用。恢复的是文件、目录、可靠正文和材料单元能力，不是把整个旧 `knowledge` 路由或 `KnowledgeBaseManager` 重新设为默认运行依赖；`legacy-knowledge` 继续只承载传统检索、向量和图谱兼容能力。

复用 `parse_document` 时，解析产物中的图片存储与读取必须走一个同时适用于资料库和专家项目、并能在默认 LITE 模式鉴权访问的共享边界。不能给专家材料传入知识库专用的图片前缀或链接，再依赖默认未注册的 `/api/knowledge/.../images/...` 路由；也不为专家项目另造一套文档解析器。

### 唯一材料事实与存储

资料库是原始文件和规范化 Markdown 的唯一事实来源。原始文件、规范化 Markdown 和解析出的图片统一保存在私有 MinIO 对象存储；PostgreSQL 保存资料库、来源文件、材料单元、对象位置、目录关系、行范围、状态、进度、错误和权限等管理事实，不把整份正文重复写入数据库。

专家项目只保存已选择材料单元的关联、标题、来源行范围和学习产物；Worker 根据该关联读取资料库中的规范化 Markdown。项目内私有目录只存笔记、Review、讲义、候选 Skill 等编译产物，不再存 `raw/` 或 `text/` 材料副本。

首版不支持修改已被专家项目引用的来源文件或材料单元，也不允许删除它们。否则正在恢复的项目会读到不同正文，既有证据行号也会失效。用户需要更新材料时，重新导入为新的来源文件和材料单元；没有被项目引用的资料仍可按资料库规则删除。

### 基础设施复用与权限边界

资料库、PostgreSQL、MinIO、Redis/ARQ、Worker、任务中心、Skill 安装、Skill 删除和共享权限都沿用现有项目的实现与调用方式。专家新增的内容只限于资料单元接入、专家项目编译服务、项目 Prompt 包、专家页面/API 适配和任务中心的专家项目投影；不另建队列、对象存储、任务中心或通用权限框架。

专家训练属于管理员能力：只有 `admin` 或 `superadmin` 可以创建专家项目、选择材料启动训练、确认两个阶段、处理编译结果、启用或卸载专家 Skill，以及删除专家项目。普通用户不能创建或驱动专家训练项目。

专家 Skill 启用后沿用现有 Skill 的共享权限和可见性计算。管理员通过已有 `share_config` 分发 Skill；普通用户只能在已有 Skill 可见范围内使用它，不能读取编译中的项目、项目工作目录或资料库中未授权的原始材料。专家项目的训练进度进入现有任务中心，发起训练的管理员和具备管理权限的用户看到项目投影，任务中心不新增一套执行事实。

### Fork 基线与功能迁移纪律

这项改造以 Fork 时已有项目为基础：先找回仍服务于当前用户流程的原有功能，再把它们接到专家主线。不能因为新增专家项目，就让上传、目录、解析、正文预览、失败重试、进度或任务管理等既有体验无故消失。任何不能原样沿用的旧入口，都要在实施说明和验收中写清三个事实：旧功能服务的对象、它为什么不能直接复用、用户在新主线中由哪个明确入口完成同一件事。

任务中心的“删除”是已经观察到的一条具体差异。`4a0110d1` 为 Tasker 任务增加了 `DELETE /api/tasks/{task_id}` 和终态任务卡的删除按钮；`d08b74be` 将专家项目加入任务中心时，专家项目卡只是 PostgreSQL 项目事实的只读投影，ID 为 `expert-project:<project_id>`，不对应 Tasker 的任务记录。旧按钮若直接沿用，会调用通用 Tasker 删除接口并得到 `404`。当前前端对 `expert_project` 隐藏删除按钮，是在避免这个确定的错误，不表示专家项目已经有等价的删除能力。

本轮应补齐两个明确动作，且都由专家项目页面发起，不复用 Tasker 删除入口：

- **删除专家项目**：只允许暂停或未运行、且未启用 Skill 的项目。已启用时必须先卸载 Skill，避免留下无法追溯的已安装成品。删除项目事实、笔记、Review、讲义和候选 Skill 工作目录，但绝不删除资料库中的原始文件、规范化 Markdown 或材料单元。
- **卸载已启用专家 Skill**：复用现有通用 `delete_skill` 的单一删除实现，删除已安装 Skill 后将项目恢复为候选成品可再次启用的状态；不删除项目记录、候选成品或资料库材料。

### 既有专家前端接入的前置缺口

资料库选材接入不能绕开当前专家项目主链已经存在的以下缺口。这些是第 C 阶段开始前需要修正的真实用户流程问题，不是顺手重构项。

1. **专家训练权限和任务中心合同需要统一。** 专家训练只允许 `admin` 或 `superadmin` 创建、选材、推进确认、启用、卸载和删除；专家路由全部使用管理员依赖，前端对普通用户隐藏创建和训练入口。专家项目进度进入现有任务中心，由发起训练的管理员和具备管理权限的用户查看；普通用户不读取编译中的专家项目，只通过已有 Skill 共享权限使用已启用 Skill。若通用 Tasker 仍需支持普通用户读取其他任务，单独维持其现有权限合同，不把专家项目混入普通用户视图。
2. **材料卡点后的暂停缺失。** 已冻结流程要求用户在“需要处理”时可以修复重跑、明确排除或暂停项目。当前详情页和 API 已有前两者，没有暂停入口或持久化状态。实施时补一个最小的项目暂停动作：项目事实明确记录暂停，ARQ 恢复扫描不重投暂停项目，任务中心和项目页显示暂停；恢复由用户显式触发，不能把暂停当作“需要处理”或静默继续执行。
3. **任务路由集成测试仍是旧权限合同。** `backend/test/integration/api/test_task_router.py` 需要按新的专家训练权限重写：管理员可以读取自己发起的专家项目投影，具备管理权限的管理员可以按现有范围查看；普通用户不能创建或读取编译中的专家项目；通用 Tasker 的普通用户合同与管理员取消/删除合同分别保持清晰。
4. **前端测试没有覆盖主流程。** 现有 `web/test/unit/expertProject.test.js` 和 `responsiveLayout.test.js` 只覆盖展示映射、视口判断和部分源码约束，不能证明管理员创建项目、资料库选材、人工模式两次确认、自动推进、材料卡点、任务中心、预览启用、Skill 分发和删除/卸载流程。每项主链改动完成后，在 Docker Compose 环境补接口测试和浏览器黑盒验证；当前 `web-dev` 只挂载 `web/src`，执行前端测试的容器路径也必须能访问 `web/test`。
5. **任务中心把等待确认误报为完成。** 当前专家项目投影把正文就绪待选样本和人工模式的等待确认映射为 Tasker 的 `success`，页面因而显示“已完成”。实施时增加专家项目专用的“等待用户操作”展示状态，或由前端根据项目状态渲染等价语义；这些状态不能归入完成筛选、写入完成时间，也不能让用户误以为确认已经跨过。自动模式获得首次授权后应继续显示真实运行状态。
6. **逐份学习绕过已有 ARQ 调度。** 当前实现把一个项目的所有材料塞入单个 ARQ job 后，在进程内用 semaphore 和 `asyncio.gather` 调度，并为所有异常加自定义重试。这重复了已有 Worker 调度，且会让一个项目绕过统一容量控制。实施时改为每份材料一个稳定 ARQ job，复用已有任务投递和可识别临时失败的重试边界；确定性的合同、上下文或输入错误直接进入“需要处理”。
7. **含图材料没有正确的默认运行合同。** 当前专家正文解析虽然复用了统一入口，但传入的图片前缀不符合旧知识库图片 URL 合同，默认 LITE 也不注册旧图片路由。实施时只共享图片产物的存储和授权读取边界，不复制解析器或复活旧知识库路由；必须用真实 DOCX、PDF 或 OCR 图片材料验证。

8. **当前资料库事实模型仍未从旧知识库耦合中拆出。** `KnowledgeFile` 依赖 `knowledge_bases.kb_id`，旧知识库路由和管理器在 LITE 下不初始化。实施时复用旧上传、目录、解析、对象存储和正文预览能力，但资料库的来源文件、规范化正文和材料单元必须有独立的事实边界，不依赖旧 `KnowledgeFile` 的 KB 外键、chunk 状态或旧路由。

9. **架构地图必须同步。** `ARCHITECTURE.md` 仍描述专家项目直接上传并保存项目私有 `raw/`、`text/`。在实施资料库接入前，必须改成“资料库统一持有原始文件和规范化 Markdown，专家项目只保存材料关联与编译产物”，避免代码地图把实现带回废弃入口。

## 用户流程

### 1. 建立资料库并导入材料

用户在资料库中创建或进入一个资料集合，建立目录后批量上传文件或目录中的文件。资料库展示每个文件的名称、所在目录、类型、处理状态、当前进度和失败原因。用户可以对失败文件重试；重试只处理该文件，不影响已经完成的文件。

资料库处理完成后，用户可以查看完整可靠正文和其来源行范围。资料库展示的是文件处理事实，不把“已经上传”伪装成“已经可供专家学习”。只有正文可读、结构范围已形成且自然主题边界已确认的单元，才会显示为可选材料。

### 2. 处理长书和长材料

短文、完整口述稿或其他本身已经能独立阅读的文件，可以直接形成一个材料单元。它们以来源文件标识和归一化 Markdown 中的完整正文行范围定位。长书、合集、课程记录和其他长材料先保留整份完整正文，再根据正文中已经存在的标题或用户提供的目录做粗粒度候选范围。

粗分只提供候选范围和来源定位，不做主题判断。它不按字数截断，不把 Markdown 标题的正则匹配当成“内容已经分好”，也不因为某段文字短或长就自动合并或拆开。

随后由模型执行边界确认任务。每个任务接收当前候选范围、相邻范围的完整正文，以及可用的来源结构和位置，判断下列事情：

- 当前边界是否已经包住一个可以完整独立阅读的自然主题；
- 两个相邻范围是否应合并，或一个范围是否应按其内部真实主题拆开；
- 每个确定单元应该叫什么，以及它在来源正文中的行范围；
- 哪些范围因解析丢失结构、正文不完整或无法形成自然单元而需要处理。

模型返回的是内容判断及边界决定，系统只机械保存单元、标题和来源行范围。模型不能自行浏览资料库目录或决定处理进度；系统为当前边界任务提供需要的完整正文和相邻上下文。若一份长材料无法在已有标题或目录结构中形成模型能够完整阅读的有意义范围，流程进入“需要处理”，由用户补充结构、拆分来源文件或调整资料范围，不能暗中截取一段继续。

用户在资料库中看到最终的材料单元及其来源行范围，再从中选择进入专家项目。长材料可以同时显示正文中保留的标题；短文显示来源文件和完整正文行范围。这里的选择确认材料范围，不新增专家学习流程之外的人工审批门槛。

### 3. 从资料库创建专家项目

创建项目时，用户填写项目基础信息并选择一组已经就绪的材料单元。系统建立项目与材料单元的关联，记录标题、来源标识和来源行范围；项目读取资料库中统一管理的规范化 Markdown，不复制完整正文。项目不重新上传、不重新 OCR、不重新解析这些材料。被项目引用的材料不能被资料库覆盖或删除，因此学习输入和证据行号保持稳定。

之后的第 0 阶段只从已选择的就绪材料中选择代表材料；第 1 阶段以一个自然材料单元为最小独立学习任务。模型每次读取的是该单元的完整正文，而不是单元的一段 RAG chunk。项目在材料、学习、Review、主题和讲义阶段继续保存自身的正式状态与产物，并沿用两个既定确认点。

## 资料结构与章节化

本轮只引入当前流程需要的三类事实；字段名和表结构留到确认后结合现有迁移方式确定。

| 事实 | 职责 | 必要内容 |
| --- | --- | --- |
| 资料库 | 用户管理的一组来源材料与目录 | 所有者、名称、目录树 |
| 来源文件 | 一份原始文件及其完整正文处理结果 | 所属目录、私有原始文件位置、私有规范化 Markdown 位置、处理状态、进度、失败原因 |
| 材料单元 | 从一个就绪来源文件中确认出的完整可读范围 | 所属来源文件、标题、归一化 Markdown 行范围、单元状态 |

来源文件和材料单元分开保存，避免把“一个文件已经解析”误当成“它已经能被专家项目完整学习”。材料单元必须能回到来源文件：至少保存来源文件标识和归一化可靠正文中的稳定行范围；正文中已有的标题或用户提供的目录只作为候选结构。短文缺少标题不构成失败。只有长材料既缺可用结构、又无法形成可完整读取的范围时，才进入“需要处理”。

章节化由两个清晰步骤组成：

```text
完整正文 + 可见标题或用户提供的目录
-> 结构候选范围（机械保留标题、目录和行范围）
-> 模型阅读候选范围与相邻完整上下文
-> 确认、合并或拆开自然主题边界
-> 带来源定位的材料单元
```

第一步不承担语义判断，第二步不靠程序启发式代替模型阅读。这样“粗分”解决长材料的输入组织问题，“确认边界”解决内容完整性问题。材料单元的长度由主题和可完整阅读性决定，不由预设字数决定。

资料库处理状态保持最小且可解释：等待处理、处理中、需要处理、正文就绪、单元处理中、单元就绪。项目侧只允许选择“单元就绪”的材料。项目暂停是项目事实，不是资料或材料单元状态；具体执行尝试次数和队列信息由任务记录保存，不把它们混入用户面对的材料语义状态。材料单元一旦被项目引用，资料库只允许查看，不允许覆盖或删除；项目删除后解除该引用。

## 分阶段最小实施范围

### 阶段 A：资料库文件处理

- 先恢复旧知识库已有的批量上传、目录管理、文件展示、OCR、解析、确定性格式归一化、完整正文预览与失败重试能力，再做接入专家材料单元所需的最小改造。
- 恢复原有目录上传队列，保留相对路径、逐文件进度和单文件失败重试；不能只用一个大 multipart 请求或 ZIP 替代用户直接导入资料目录的已有体验。
- 在恢复的文件事实之上补齐资料库和材料单元所需记录；只增加专家项目当前确实消费的单元关联，不另起一套重复的上传和解析实现，也不依赖旧知识库的向量与图谱表或状态。
- 通过 ARQ 逐文件处理；每个文件使用稳定任务标识，状态、进度、错误原因和正文结果持久化，Worker 重启后只重投未完成文件。
- 资料库接口在默认 `LITE_MODE=true` 可用，不初始化旧知识库运行时，也不触发向量、图谱或旧检索路由。
- 复用统一解析入口时，让资料库和专家项目都能以各自授权读取解析出的图片；用真实含图材料验证，不接受图片被替换为占位文字或不可访问链接。
- 在资料库和任务中心展示同一份持久化处理事实。

完成本阶段后，用户可以可靠地管理文件并得到可查看的完整正文，但长材料还不能进入专家项目。

### 阶段 B：结构范围与自然主题材料单元

- 从归一化完整 Markdown 中保存可见标题和行范围，形成粗粒度候选范围。
- 增加模型边界确认任务，产出可独立完整阅读的材料单元、标题和来源正文行范围。
- 处理边界不清、正文缺失或无法形成自然单元的来源文件，并提供针对该来源的重试或人工处理入口。
- 只有已确认的材料单元可供选择；不创建、不写入也不显示旧 `KnowledgeChunk` 作为专家材料。

完成本阶段后，长材料的自然主题单元可以被单独选择，且每个单元都能回到规范化正文的行范围。

### 阶段 C：专家项目从资料库选材

- 将新项目入口改为选择资料库中的就绪材料单元，不再把上传控件作为新项目的材料来源。
- 已有直接上传项目继续从其现有项目记录和项目私有材料中兼容读取并恢复，不迁移到资料库，也不恢复新增、替换或再次上传材料的入口。
- 在项目材料事实中保存资料库单元关联、标题和来源行范围，以供材料预览、第 0 阶段、学习、Review 和最终证据映射使用；完整正文始终从资料库读取。项目创建后，被引用材料不能在资料库中更新或删除，因此不影响项目恢复和证据定位。
- 逐份学习使用“项目 + 材料 + 方法版本”稳定标识的独立 ARQ 工作；单份工作只执行笔记、Review 和有限修订。阶段交接只读取持久化材料事实，不在单个项目级 ARQ 工作中用 `asyncio.gather`、项目私有 semaphore 或捕获所有异常的自定义重试调度全部材料。
- 复用现有专家项目后续阶段：代表材料选择、人工模式的两个确认点、自动模式的一次授权、逐份学习、Review、总编串行编写、预览和手动启用。
- 保持项目状态为事实来源，ARQ 为执行者，任务中心为只读投影；不通过 API 进程内 Tasker 恢复资料库或专家项目。正文就绪待选样本、人工模式的等待确认和暂停均显示为等待用户操作，不能投影为“已完成”；自动模式中已经获得授权的阶段继续显示真实运行状态。

完成本阶段后，一条可用主链从“资料库已处理单元”进入“已启用专家 Skill”，且专家项目不会再次上传同一来源文件。

## 验收标准

- 用户可以在资料库中直接批量上传文件或目录，保留目录相对路径，看到每份文件的解析进度、完整正文、失败原因和单文件重试结果。
- 正常文件的 OCR、解析和确定性格式归一化完成后，用户可以查看完整正文；失败或空正文不会被标记为可选专家材料。
- 默认 `LITE_MODE=true` 下，资料库文件、目录、可靠正文和材料单元接口可以使用，但不初始化旧知识库运行时，也不启动 embedding、Milvus、向量入库或图谱构建。
- 以一篇短 Markdown 材料和一份包含明确标题的长 Markdown 材料验证：短文以来源文件和完整正文行范围定位；长文先保留整份归一化正文，再得到多个自然主题材料单元。每个单元可独立完整阅读，并显示可追溯的来源行范围。
- 验证过程不得以固定字符数、固定 token 数、正则主题猜测或隐式位置采样替代模型对边界的内容判断；模型确认任务必须读取当前范围和必要的相邻完整上下文。
- 用真实含图材料验证解析后的图片能在资料库和专家项目预览中按权限读取，不依赖 `/api/knowledge` 的旧图片路由。
- 新建专家项目只能从资料库中选择“单元就绪”的材料；项目不要求再次上传，也不重复 OCR 或解析。被项目引用的来源资料不能覆盖或删除；项目始终从资料库读取同一份规范化正文，恢复能力和证据行号保持不变。已有直接上传项目继续按现有记录兼容读取和恢复，但不能新增、替换或再次上传材料。
- 第 0 阶段与第 1 阶段分别读取代表材料和完整材料单元，不读取 RAG chunk。人工模式保留两个确认点；自动模式必须由用户在第一次方法与小样确认时明确开启，此后可以跳过方法 V2 和组织确认，但不能跳过首次授权或候选 Skill 的手动启用。
- 默认专家材料流程不触发 embedding、Milvus、向量入库或图谱构建。启用 `legacy-knowledge` 的传统检索行为不改变资料库到专家项目的主链。
- 资料库文件处理和专家逐份学习均由独立 ARQ 工作执行；单份失败、重试或 Worker 中断不重新执行已经完成的其他文件或材料，且不由项目级 semaphore 绕过 Worker 与供应商容量。
- 资料库文件处理、单元确认和专家项目在 API 或 Worker 重启后仍能根据 PostgreSQL 事实恢复未完成工作；任务中心能展示进度和失败摘要，但删除或关闭任务中心不影响恢复。正文就绪、人工模式的等待确认和暂停不会显示为“已完成”，自动模式不会因任务中心状态丢失推进授权。
- 自动推进只消费第一次确认时持久化的 `auto_advance`。新页面默认开启；历史项目和旧 API 默认关闭。自动模式完成后项目停在候选 Skill 预览，不自动启用。
- 自动模式的材料采用、修订和排除由模型判断。运行条件正常时，普通内容问题不会转成人工逐项确认；零份材料通过 Review，或全部通过笔记都被总编明确列为未分配时，项目以具体原因停止，不以固定材料数量判断可信度。
- 删除专家项目只删除项目记录与项目编译产物，不删除资料库材料；卸载已启用专家 Skill 只删除安装后的 Skill，不删除候选成品或项目记录。
- 最终专家 Skill 仍只包含讲义、导航、精选证据、来源映射和 `SKILL.md`，不包含资料库的完整正文或章节化过程产物。

## 风险与待 Owner 确认

1. **资料库的可见范围。** 旧知识库当前偏管理员管理；资料库若面向所有可创建专家项目的用户，需要确认私有、共享和授权规则，避免项目选择到无权阅读的来源。
2. **已被项目使用的材料如何更新。** 首版采用唯一资料事实来源：被项目引用的来源文件和材料单元不能覆盖或删除，项目只保存关联并读取资料库统一管理的规范化正文。更新材料需要重新导入为新的来源文件和材料单元；若以后需要让项目跟随更新，再单独设计版本关系。
3. **来源定位的最低要求。** 首版只要求来源文件和归一化 Markdown 的稳定行范围。正文中没有可用标题、又无法形成可完整读取范围的长材料，默认标为“需要处理”，不伪造结构位置。
4. **已有专家项目的过渡（已确认）。** 已经直接上传材料的项目从现有记录和项目私有材料中兼容读取、恢复并完成原流程；不迁移到资料库，也不保留新增、替换或再次上传材料的兼容入口。
5. **章节化模型的执行成本。** 边界确认是有内容判断的模型任务。首版应先用真实长书验证候选范围与调用数量，再定并发和预算，不在此时预设固定长度阈值或重试循环。
6. **删除运行中项目的交互。** 当前 Worker 会继续执行已投递任务，因此首版要求先暂停再删除；项目页面需要把这一条件说清楚，不能在运行中直接删除项目事实。
